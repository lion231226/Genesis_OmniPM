## D2. PI Agent 原生适配（核心改造）

### D2.1 状态机 ↔ PI agent-core 事件循环映射

PI Agent 的 ReAct 循环天然匹配 OmniPM 的 Step A→E 迭代模式：

| OmniPM 概念 | PI agent-core 对应 | 适配方式 |
|-------------|-------------------|---------|
| 状态转换 | `turn_start` → `turn_end` 事件 | 每个 OmniPM 状态对应一个或多个 PI turn |
| GATE 暂停等待用户 | `steeringMode: "one-at-a-time"` | 利用 PI 的 steering 机制注入用户确认 |
| Step B 8 专家评审 | 8 个并行 `AgentTool` 调用 | 声明为 PI tools，利用 `toolExecution: "parallel"` |
| Step C 开发任务 | 工具调用序列（Read/Write/Bash） | PI 原生工具 + 项目安装的 Skill |
| Step D 测试 | 工具调用 + 输出解析 | `npm test` 等命令通过 PI Bash 工具执行 |
| CHECKPOINT 写入 | `afterToolCall` hook | 每个关键步骤完成后自动写 PROJECT_MEMORY.md |
| 中断恢复 | `agentLoopContinue()` | 读取 PROJECT_MEMORY.md 的 `resume_point` 恢复 |

### D2.2 利用 PI 原生机制简化 OmniPM

| PI 原生能力 | 对 OmniPM 的简化 |
|------------|-----------------|
| `AGENTS.md` 自动加载 | OmniPM 不再需要"复制粘贴到新会话"——放入项目根目录即自动生效 |
| `beforeToolCall` / `afterToolCall` hooks | 安全门禁可以在工具执行前后挂钩，而非纯文本指令 |
| `steering` 消息 | GATE 确认块可以直接利用 PI 的 steering 队列，而非"等待文本回复" |
| `transformContext` | 长会话退化监控可以在这里做上下文剪枝，而非提示词内自检 |
| `terminate: true` | Step 完成信号可以触发 PI 循环优雅退出 |
| `sessionId` | SESSION_CONTEXT 可以用 PI 的 session ID 替代自建追踪 |

### D2.3 专家评审的 PI 化改造（Step B）

**v0.3.0 方式**：提示词指令 → Agent 依次扮演 8 位专家 → 输出文本块

**v1.0.0-PI 方式**：利用 PI Agent 的 Subagent 机制（如果可用）或并行 Tool 调用：

```
方案A（推荐，如果 PI 支持 Subagent）：
  - 声明 8 个评审专家为独立 Subagent
  - 并行触发，各自评审设计报告
  - Orion 收集结果后综合决策

方案B（降级，如果 Subagent 不可用）：
  - 利用 PI 的 toolExecution: "parallel"
  - 每个专家评审封装为一个 AgentTool
  - 并行执行，结果汇总
```

### D2.4 安全门禁 PI 化（Step C）

PI Agent 的技术栈是 TypeScript（93.2%），安全门禁需新增：

| 禁止模式 | 语言 | PI 场景 |
|---------|------|--------|
| `eval()` | TypeScript/JavaScript | PI 自身代码生成 |
| `new Function()` | TypeScript/JavaScript | 动态代码执行 |
| `import()` 动态导入 | TypeScript/JavaScript | 绕过编译检查 |
| `child_process.exec()` 无校验输入 | TypeScript/JavaScript | PI 工具调用中的命令注入 |
| `! ` 前缀命令（PI 的 shell 转义）中拼接用户输入 | PI 命令 | 命令注入风险 |

## D3. 能力自发现层（CDL — Capability Discovery Layer）★ 核心新增 — PI + GitHub 双生态

> **详细筛选标准与质量门禁**见独立模块 `modules/cdl_quality_gate.md`。本节描述 CDL 的架构设计和与 OmniPM 工作流的集成方式。

### D3.1 设计目标

OmniPM 在 PI Agent 中运行时，可以根据项目需求**主动**执行以下操作：

1. **搜索**：在 6 级安装源（Skills Registry → npm → GitHub 已验证组织 → GitHub 社区 → GitHub 个人 → 本地）中并行搜索匹配的能力
2. **筛选**：对每个候选执行**五维质量评分卡（Q-Score）**——安全性(30%)、活跃度(20%)、社区验证(25%)、功能匹配(15%)、可维护性(10%)
3. **分级**：Q-Score ≥75 🟢自动通过 / 50-74 🟡人工审查 / <50 🔴拒绝；另设 8 项一票否决条件
4. **安装**：执行安装命令（`npx skills add ...`、`npm install ...`、`gh repo clone ...`）
5. **配置**：将能力写入 `.pi/skills.yaml` 或 `.pi/mcp.yaml`，含 Q-Score 和安装时间戳
6. **验证**：安装后执行最小验证（命令可用性检查），确认成功
7. **监控**：每次会话启动时健康检查已安装能力（是否弃用、是否有安全更新）

### D3.2 CDL 触发时机

```
项目类型识别完成（§3.2 步骤1）
    │
    ▼
能力需求分析（§3.2 步骤1.5 新增）
    │  根据项目类型 + 技术栈 + 功能需求
    │  生成《能力需求清单》
    │
    ▼
CDL 搜索与匹配（双生态并行）
    │  对清单中每项能力：
    │  ├── PI 生态搜索：Skills Registry / npm / MCP Registry
    │  │   └── 搜索 Skill、Subagent、MCP Server、Workflow
    │  ├── GitHub 生态搜索：Verified Orgs / Community / Personal repos
    │  │   └── 搜索 Actions、Dev Containers、模板仓库、CLI 工具、参考实现
    │  ├── 评估匹配度 + 质量评分（Q-Score）
    │  └── 输出推荐列表 + 安装计划
    │
    ▼
用户确认 → 安装 → 写入 .pi/ 配置
    │
    ▼
进入 Step A 设计（使用已安装的能力）
```

### D3.3 能力需求分析模板

OmniPM 在完成项目类型识别后，输出以下结构化分析：

```markdown
## [能力需求分析] <项目名称>

### 技术栈能力需求
| 能力类型 | 需求描述 | 搜索生态 | 推荐搜索关键词 |
|----------|---------|---------|---------------|
| Skill | Supabase 数据库操作 | PI | `supabase` `database` |
| Skill | React 前端开发 | PI | `react` `frontend` |
| MCP | GitHub API 操作 | PI | `github` |
| MCP | Playwright 浏览器测试 | PI | `playwright` `browser` |
| Subagent | 代码审查 | PI | `code-review` |
| Workflow | 全栈项目 CI/CD | PI | `fullstack` `cicd` |
| GitHub Action | 自动部署到 Vercel | GitHub | `vercel` `deploy` `action` |
| Dev Container | 标准化开发环境 | GitHub | `devcontainer` `node` `postgres` |
| CLI 工具 | 数据库迁移工具 | GitHub/npm | `prisma` `drizzle` `migrate` |
| 参考实现 | 全栈项目脚手架 | GitHub | `starter` `template` `fullstack` |

> **能力类型不限于上表所列**。CDL 根据项目实际需求动态扩展搜索范围——任何能提升项目效率的 PI 或 GitHub 生态资产均可纳入搜索。

### 搜索策略（双生态并行）
1. **PI 生态**（优先）：
   - Skills Registry（`npx skills search <keyword>`）
   - npm Registry（`npm search <keyword>`）
   - MCP Registry（`@modelcontextprotocol/*`）
2. **GitHub 生态**：
   - Verified Organizations（`anthropics`、`supabase`、`vercel`、`earendil-works` 等）
   - Community repos（Stars ≥ 50，最近 6 个月有更新）
   - GitHub Actions Marketplace（`actions/*`）
   - Dev Container templates（`ghcr.io/devcontainers/*`）
3. 优先搜索已安装的全局能力（避免重复安装）
4. 评估搜索结果（Q-Score 五维评分 + 一票否决）
5. 输出安装计划，等待用户确认
```

### D3.7 CDL 安装协议（安全约束）

由于 PI Agent **无内置权限模型**，CDL 的安装操作必须遵循 OmniPM 的安全协议：

1. **安装前必须输出完整审查信息**（类似 §2.3(c) 依赖审查）：
   ```
   ## [能力安装审查] <能力名称>
   - 类型: Skill / MCP / Subagent / Workflow
   - 来源: npm registry / GitHub / skills registry
   - 版本: <version>
   - 用途: <项目中的具体用途>
   - 权限需求: <需要的文件/网络/Shell 权限>
   - 安全评估: <已知风险>
   请确认是否安装？[确认/拒绝]
   ```

2. **安装范围限制**：仅安装在项目级 `.pi/` 目录，不污染全局环境。

3. **来源白名单**：PI 生态从 Skills Registry 和 npm registry 安装；GitHub 生态从已验证组织（`anthropic`、`supabase`、`vercel`、`earendil-works`、`actions` 等）和社区高信誉仓库（Stars ≥ 50 + 最近 6 个月活跃）安装。

### D3.8 GitHub 生态能力发现

除 PI 原生 Skill/Subagent/MCP 外，CDL 在 GitHub 生态中可发现和集成以下能力类型：

| GitHub 能力类型 | 发现方式 | 集成方式 | 示例 |
|----------------|---------|---------|------|
| **GitHub Actions** | `gh search repos --topic=github-actions` | 复制到 `.github/workflows/` | `actions/setup-node`、`peaceiris/actions-gh-pages` |
| **Dev Container 模板** | `gh search repos --topic=devcontainer` | 生成 `.devcontainer/` | `mcr.microsoft.com/devcontainers/typescript-node` |
| **项目模板/Starter** | `gh search repos --topic=starter-template` | Clone → 适配 | `vercel/next.js/examples/` |
| **CLI 工具** | `npm search` / `gh search repos` | `npm install -D` 或全局安装 | `prisma`、`drizzle-kit`、`tsx` |
| **参考实现** | `gh search repos --topic=<tech>-example` | Clone → 提取模式 → 适配 | 官方示例仓库 |
| **Hooks/Plugins** | `gh search repos --topic=<framework>-plugin` | `npm install -D` | ESLint plugins、Prettier configs |
| **配置预设** | `gh search repos --topic=<tool>-config` | 复制配置文件 | `tsconfig.json` bases、`.eslintrc` presets |

**GitHub 搜索质量门禁**（高于通用 Q-Score 的额外要求）：
- Stars ≥ 50 或来自 Verified Organization
- 最近 6 个月内有 commit
- LICENSE 文件存在且为 MIT/Apache-2.0/BSD 等宽松协议
- 不在 GitHub Advisory Database 中有未修复的安全漏洞
- `README.md` 存在且≥200 字（排除废弃/占位仓库）

### D3.9 CDL 能力类型扩展原则

CDL 的能力类型列表**不是封闭枚举**。随着 PI 和 GitHub 生态演进，新的能力类型会持续出现。CDL 遵循以下扩展原则：

1. **向后兼容**：新能力类型不需要修改 CDL 核心架构——通过配置驱动发现
2. **生态自适应**：CDL 查询时动态检索当前可用的能力类型，而非依赖静态列表
3. **用户可扩展**：`.pi/config.yaml` 中支持 `custom_sources` 字段，用户可添加私有/企业内部源
4. **渐进式集成**：优先级：PI 原生（Skill/MCP）> npm 包 > GitHub Actions > 参考实现 > 手动

```yaml
# .pi/config.yaml 示例——用户自定义扩展源
custom_sources:
  - name: "internal-gitlab"
    type: "gitlab"
    url: "https://gitlab.internal.example.com"
    auth: "${GITLAB_TOKEN}"
  - name: "team-templates"
    type: "github-org"
    org: "my-team-org"
```

```
    │

  需求对齐 → 类型识别 → 能力需求分析 → CDL 安装 → Step A~E
```

### D4.2 棕地项目（Brownfield）入口流程

```
cd existing-project/
pi .   ← PI Agent 启动
    │
    ▼
Orion 检测：目录中存在既存代码（package.json / pyproject.toml / go.mod / ...）
    │
    ▼
"检测到既存项目。正在分析项目结构..."
    │
    ▼
扫描分析阶段：
  ├── 读取 package.json / pyproject.toml / go.mod 等 → 识别技术栈
  ├── 读取项目目录结构 → 识别项目类型和规模
  ├── 读取现有 AGENTS.md / CLAUDE.md / README.md → 提取项目上下文
  ├── 运行 git log --oneline -20 → 了解最近开发活动
  └── 生成《项目现状分析报告》
    │
    ▼
"项目分析完成：【分析摘要】。是否由 OmniPM 接管此项目？[确认/拒绝]"
    │
    ▼
用户确认后：
  ├── 生成 PROJECT_PANORAMA.md（基于现状分析）
  ├── 能力需求分析（基于既存技术栈）
  ├── CDL 搜索 → 安装 → 配置
  └── 进入当前最需要的工作阶段（用户指定 或 自动判断）
```

### D4.3 棕地项目分析维度

| 维度 | 分析内容 | 数据来源 |
|------|---------|---------|
| 技术栈 | 语言、框架、数据库、部署方式 | `package.json` / `pyproject.toml` / `go.mod` |
| 项目规模 | 文件数、代码行数、模块数 | `find . -name '*.ts' | wc -l` 等 |
| 项目状态 | 开发中/维护中/停滞 | `git log` 活跃度 |
| 现有工具链 | Lint/Test/Build/CI 配置 | `.eslintrc` / `jest.config` / `.github/workflows/` |
| 现有 AI 配置 | 已有的 AGENTS.md / CLAUDE.md | 文件内容 |
| 代码质量信号 | TypeScript 严格模式、测试覆盖率 | `tsconfig.json` / 测试文件比例 |
| 依赖健康度 | 过期依赖、已知漏洞 | `npm outdated` / `npm audit` |

## D7. 关键设计风险

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| PI Agent 的 Subagent 机制是否成熟 | 中 | Step B 降级方案：并行 Tool 调用替代 Subagent |
