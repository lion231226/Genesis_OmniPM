# OmniPM v2.0.0 — 自编排工作流引擎重构 · 设计报告

> 设计日期：2026-07-21 | 设计人：Meta-Orion | 目标：静态流水线 → 动态自编排引擎

---

## 摘要

v2.0.0 做一件事：**让 Orion 从"按剧本演戏"变为"自己写剧本"**。

v1.0.0-PI 的本质是一本详尽的操作手册——固定的 5 步管道、固定的 8 人评审团、固定的 7 维度设计。它能工作，但它是**盲目的**。用 8 个专家评审一个纯后端 API 项目，其中 3 个专家的意见毫无价值。

v2.0.0 的 Orion 不再执行预编脚本。它先分析项目，然后自己决定：需要几步？需要哪些专家？哪些维度重要？质量门控放在哪里？

## D1. 核心架构：Meta-Orion + Execution-Orion 双层模型

```
┌──────────────────────────────────────────────────────┐
│                   Meta-Orion（元层）                   │
│                                                      │
│  输入：用户项目描述                                    │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │ 深度分析  │→│ 风险画像  │→│ 域识别    │           │
│  └──────────┘  └──────────┘  └──────────┘           │
│        ↓              ↓              ↓               │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │ 生成DAG  │  │ 组装专家团│  │ 维度加权  │           │
│  └──────────┘  └──────────┘  └──────────┘           │
│                                                      │
│  输出：执行计划（Workflow DAG + Expert Panel + Gates） │
└──────────────────────┬───────────────────────────────┘
                       ↓
┌──────────────────────────────────────────────────────┐
│                Execution-Orion（执行层）               │
│                                                      │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐       │
│  │ DAG 执行  │───→│ 专家调度  │───→│ 闭环监控  │       │
│  └──────────┘    └──────────┘    └──────────┘       │
│       ↑                               │              │
│       └────── 偏差检测 → 自动修正 ←───┘              │
│                                                      │
│  输出：交付物（代码 + 文档 + ADR + 测试报告）          │
└──────────────────────────────────────────────────────┘
```

### D1.1 双层职责边界

| 层 | 职责 | 输入 | 输出 | 频率 |
|----|------|------|------|------|
| **Meta-Orion** | 分析、规划、设计工作流 | 项目描述 | 执行计划 | 项目启动时执行 1 次 |
| **Execution-Orion** | 执行、监控、修正 | 执行计划 | 交付物 | 贯穿整个项目 |

## D2. Meta-Orion：从关键词匹配到深度分析

### D2.1 分析维度

v1.0.0-PI 用关键词统计来路由项目类型。v2.0.0 替换为真正的分析：

```
【旧】Router: "包含'记账'+'Web' → DEV类型 → 加载开发型工作流"
【新】Meta-Orion:
  1. 领域分析：这是什么业务？谁在用？核心流程是什么？
  2. 技术分析：隐含的技术约束？集成复杂度？数据敏感度？
  3. 风险分析：安全风险？性能瓶颈？可用性要求？数据一致性？
  4. 域识别：哪些技术域被涉及？(API设计/数据库/前端/安全/性能/部署)
  5. 复杂度评估：规模估算？不确定性？团队能力假设？
```

### D2.2 输出：ProjectProfile

```yaml
project_profile:
  type: "开发型"           # 主导类型
  sub_types: ["API服务"]   # 子类型
  risk_matrix:
    security: "🔴 高"      # 涉及支付
    performance: "🟡 中"
    data_consistency: "🔴 高"
    availability: "🟡 中"
  domains_involved:        # 哪些域需要关注
    - {domain: "API设计", weight: 1.0}
    - {domain: "数据库", weight: 0.9}
    - {domain: "安全合规", weight: 1.0}
    - {domain: "部署运维", weight: 0.3}
    - {domain: "前端", weight: 0}       # ← 无关！
    - {domain: "SEO", weight: 0}        # ← 无关！
  complexity: "中等"
  estimated_steps: 5       # Meta-Orion 自己判断需要几步
```

## D3. 工作流 DAG：从固定管道到有向无环图

### D3.1 为什么是 DAG 而不是管道

```
管道（v1.0.0-PI）：            DAG（v2.0.0）：
                                     
A → B → C → D → E            [安全Review] ←─┐
                                  ↓          │
永远按这个顺序                   [API设计] ──→ [数据库设计]
不能跳过                                ↓
不能并行                         [开发实现] ←──┘
不能条件分支                          ↓
                              [渗透测试] → [压力测试]
                                    ↓
                                  [交付]
```

### D3.2 节点类型

| 节点类型 | 说明 | 示例 |
|----------|------|------|
| `ANALYSIS` | 分析节点 | 需求澄清、风险分析 |
| `DESIGN` | 设计节点 | API 设计、DB Schema 设计 |
| `REVIEW` | 评审节点 | 安全评审、架构评审 |
| `DEVELOP` | 开发节点 | 编码实现 |
| `TEST` | 测试节点 | 单元测试、渗透测试 |
| `DELIVER` | 交付节点 | 文档、部署 |
| `GATE` | 质量门控 | 用户确认点 |

### D3.3 连接规则

```
DESIGN → REVIEW（设计后必须评审相关域）
REVIEW → DEVELOP（通过后进入开发）
TEST → DEVELOP（失败退回开发）
TEST → DESIGN（设计级缺陷退回设计）
任何节点 → GATE（关键决策点等待用户确认）
```

### D3.4 Meta-Orion 的 DAG 生成逻辑

```
输入：ProjectProfile
处理：
  1. 遍历 domains_involved，为每个 weight > 0 的域生成 DESIGN 节点
  2. 为每个 DESIGN 节点配对 REVIEW 节点（风险越高，评审专家越多）
  3. 识别并行机会（API设计 ∥ 数据库设计）
  4. 插入 GATE 节点（在不可逆决策点）
  5. 添加 DEVELOP → TEST 循环边
  6. 计算关键路径
输出：WorkflowDAG（JSON/YAML + Mermaid 可视化）
```

## D4. 动态专家系统：从固定 8 人到按需组装

### D4.1 专家调用模型

```
【旧】8 专家 × 每个项目 = 总是 8 人评审团
【新】Meta-Orion 根据 ProjectProfile 决定：
  - 调用哪些专家
  - 每个专家关注哪个设计维度
  - 专家是独立评审还是结对评审
  - 评审顺序（关键专家先发言）
```

### D4.2 专家激活条件

| 专家 | 激活条件 |
|------|----------|
| 需求分析师 | **始终激活**（所有项目都需要需求分析） |
| 系统架构师 | risk_matrix 中 architecture 权重 > 0.3 时激活 |
| 数据库专家 | domains_involved 包含"数据库"时激活 |
| 安全专家 | risk_matrix.security ≥ 🟡 时激活 |
| 前端专家 | domains_involved 包含"前端"时激活 |
| 后端专家 | domains_involved 包含"API设计"时激活 |
| 测试架构师 | complexity ≥ "中等"时激活 |
| DevOps | domains_involved 包含"部署运维"且 weight > 0.3 时激活 |
| 教学设计专家 | type = "课程型"时激活 |
| 市场分析师 | type = "方案型"时激活 |
| SEO专家 | domains_involved 包含"SEO"时激活 |
| 媒体制作专家 | type = "音视频型"时激活 |
| 内容审核专家 | type ∈ ["课程型","图文型"]时激活 |

### D4.3 专家调用强度

专家不只是"激活/不激活"——调用强度也是动态的：

| 强度 | 含义 | 触发条件 |
|------|------|----------|
| `SKIP` | 跳过 | 域不相关 |
| `LIGHT` | 快速检查 | 低风险域 |
| `STANDARD` | 标准评审 | 中等风险 |
| `DEEP` | 深度评审 | 高风险域 |
| `PAIR` | 结对评审 | 交叉域问题（如安全+API） |

## D5. 闭环修正引擎

### D5.1 闭环的三个层次

```
Level 1: 任务级闭环
  "这个函数没通过单元测试" → 修代码 → 重新测试
  
Level 2: 模块级闭环  
  "API 设计导致性能瓶颈" → 回退到 API 设计节点 → 重新设计 → 重新实现
  
Level 3: 项目级闭环
  "安全评审发现根本性架构缺陷" → 回退到架构分析 → 调整技术选型 → 重新生成部分 DAG
```

### D5.2 偏差检测规则

```
监测点：每个 DAG 节点的出口
检测项：
  - 输出质量 < 阈值？→ 触发修正
  - 发现新的风险？→ 更新 risk_matrix，可能调整后续 DAG
  - 实际复杂度 > 预估？→ 重新评估，可能拆分节点
  - 专家意见出现 P0 阻塞？→ 自动回退
```

### D5.3 根因分析替代固定回退表

```
【旧】12 条固定回退路径 → 维护成本高，覆盖不全
【新】Orion 实时判断：
  1. 问题是什么？（错误描述）
  2. 根因是什么？（代码Bug / 设计缺陷 / 需求遗漏 / 技术约束？）
  3. 最近的可修正节点是哪个？（沿 DAG 反向追溯）
  4. 回退代价多大？（受影响节点 × 已完成工作量）
  5. 向用户报告 → 确认 → 执行回退
```

## D6. 自适应质量门控

### D6.1 门控位置由风险决定

```
【旧】固定 3 个 GATE：需求 / 设计 / 交付
【新】Meta-Orion 根据 ProjectProfile 决定：
  - 高风险项目（如支付系统）：5-6 个 GATE
  - 低风险项目（如个人博客）：1-2 个 GATE
  - GATE 位置由 DAG 中的不可逆决策点决定
```
