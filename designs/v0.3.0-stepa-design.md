# OmniPM v0.3.0 Step A — 顶层设计报告

> **设计日期**：2026-07-21 | **设计人**：Orion | **版本**：v0.3.0-draft-1

---

## 摘要

v0.3.0 聚焦两大核心能力升级：（1）**混合型项目深度融合**——将当前"主导类型+补充模块"的并行模式升级为"交织工作流"，使多种项目类型的 Step A~E 在同一项目中协同而非并列；（2）**跨模型兼容性验证框架**——建立系统化的测试套件、偏差度量和适配层，确保 OmniPM 在 Claude/GPT-4o/Gemini/DeepSeek 四大家族上行为一致性 ≥90%。

---

## D1. 提示词架构设计（数据架构类比）

### D1.1 混合型深度融合：从"并行"到"交织"

**现状分析（v0.2.1）**：
- `router_logic.md` §5 定义了混合型识别规则和"主导类型+补充模块"模式
- 补充模块目前仅注入专家子集，不参与工作流步骤
- 两种类型的 Step A~E 实际上独立运行，仅在专家池层面有交集

**问题**：以"开发在线课程平台"（DEV主导 + COURSE补充）为例：
- Step A：DEV 的 7 维度设计 + COURSE 的 5 维度设计各自产出，**没有交叉引用**
- Step B：DEV 8 专家 + COURSE 6 专家各自评审，**后端专家不会评审课程内容结构，教学设计专家不会评审 API 设计**
- Step C：开发任务和课程内容任务**没有依赖排序**
- Step D：代码测试和课程质量检查**没有联合门禁**

**v0.3.0 设计方案：交织矩阵 + 交织指令**

#### 交织矩阵（Cross-Type Weaving Matrix）

为每对常见混合类型定义各 Step 的交织点：

```
混合类型对：DEV × COURSE（示例）
┌──────────┬────────────────────────────┬──────────────────────────┐
│ Step     │ DEV 产出                   │ COURSE 产出               │
│          │ （主流水线）                │ （交织注入）              │
├──────────┼────────────────────────────┼──────────────────────────┤
│ Step A   │ D1-D7 通用维度             │ D-C1~C5 课程维度          │
│  交织点  │ D1 数据架构 ← 需考虑课程    │ D-C5 平台选型 ← 需评估   │
│          │ 内容存储（视频/习题/进度）  │ 自建 vs 现有LMS的技术成本 │
├──────────┼────────────────────────────┼──────────────────────────┤
│ Step B   │ 8专家评审序列              │ 6专家评审序列             │
│  交织点  │ 联合评审会：后端专家×教学   │ 联合评审会：内容审核专家  │
│          │ 设计专家 共同评审"学习进度  │ ×安全专家 共同评审"用户   │
│          │ 追踪API"设计               │ 数据隐私与课程内容版权"   │
├──────────┼────────────────────────────┼──────────────────────────┤
│ Step C   │ 开发任务清单               │ 课程内容开发清单          │
│  交织点  │ 依赖排序：课程大纲API →     │ 依赖排序：用户系统就绪 →  │
│          │ 课时内容填充工具 → 习题引擎 │ 才能定义学习者画像        │
├──────────┼────────────────────────────┼──────────────────────────┤
│ Step D   │ 代码测试门禁               │ 课程质量门禁              │
│  交织点  │ 联合门禁：课程播放页面的    │ 联合门禁：习题提交API的   │
│          │ 认知负荷 + 前端性能         │ 评分准确性 + 后端正确性   │
├──────────┼────────────────────────────┼──────────────────────────┤
│ Step E   │ 软件交付物                 │ 课程交付物                │
│  交织点  │ 合并交付：部署手册含课程    │ 合并交付：讲师指南含平台  │
│          │ 内容初始化脚本              │ 操作说明                  │
└──────────┴────────────────────────────┴──────────────────────────┘
```

**实现方案**：定义 10 对高频混合型组合的交织矩阵（C(5,2)=10），按需加载。不覆盖的组合走通用"主导+补充"降级模式。

#### 交织指令（Weaving Directives）

在主提示词中新增 `§3.3.1 混合型项目执行` 子章节，定义以下指令原语：

| 原语 | 格式 | 语义 |
|------|------|------|

| `@CROSS_GATE:<gate_name>` | `@CROSS_GATE:perf_and_cognitive_load` | 跨类型联合质量门禁 |
| `@DEP_ORDER:<task_a>→<task_b>` | `@DEP_ORDER:user_api→learner_profile` | 跨类型任务依赖声明 |

### D1.2 跨模型适配层架构

**问题**：不同模型对同一提示词的遵循程度不同：
- **Claude**：指令遵循强，长上下文稳定，支持 200K token
- **GPT-4o**：指令遵循中等，对结构化格式有时偏差，128K token
- **Gemini 1.5 Pro**：上下文窗口极大（1M+），但对复杂指令链的持续遵循有退化
- **DeepSeek-V3**：中文理解优秀，但对多轮状态机转换的持续性需验证

**设计方案：模型适配配置层**

在主提示词前增加轻量级模型适配指令块（< 200 tokens），根据目标模型动态调整：

```markdown
## 模型适配配置（MODEL_PROFILE）
# 当前目标模型：{{MODEL_NAME}}
# 适配参数：
# - gate_confirm_insist: {{STRICT|MODERATE}}  # GATE确认严格度
# - state_tracking_frequency: {{HIGH|NORMAL}}  # 状态心跳频率
# - output_format_verbosity: {{FULL|COMPACT}}  # 输出块详细度
# - security_scan_depth: {{DEEP|STANDARD}}     # 安全扫描深度
```

**模型适配参数矩阵**：

| 参数 | Claude | GPT-4o | Gemini | DeepSeek |
|------|--------|--------|--------|----------|
| `gate_confirm_insist` | STRICT | STRICT | STRICT | STRICT |
| `state_tracking_frequency` | NORMAL | HIGH | HIGH | HIGH |
| `output_format_verbosity` | FULL | FULL | COMPACT | FULL |
| `security_scan_depth` | DEEP | STANDARD | STANDARD | STANDARD |
| `multi_expert_parallel_hint` | — | `[请依次扮演]` | `[请依次扮演]` | `[请依次扮演]` |

> `multi_expert_parallel_hint`：Claude 可并行生成多位专家评审，其他模型需显式提示"依次"以避免角色混淆。

**文件变更**：
- 新建 `MODEL_PROFILES.md`（模型适配配置表 + 已知行为特征）
- 新建 `CROSS_MODEL_TEST_SUITE.md`（20 个标准化测试用例）
- 新建 `CROSS_MODEL_VALIDATION_PROTOCOL.md`（验证流程 + 偏差记录模板）

## D2. 记忆层/状态管理

### D2.1 混合型项目的状态扩展

**当前状态机（10 状态）**对混合型项目存在盲区：
- `DEVELOPMENT` 状态不区分 DEV 开发 和 COURSE 内容开发
- 如果一个类型的子任务完成而另一个未完成，`TESTING` 无法判定入口条件

**设计方案：混合型子状态标记**

在现有状态枚举表中新增 2 个混合型专用子状态标记（不改变状态机主路径）：

```
DEVELOPMENT.mixed  = DEV 和 CONTENT 子任务并行，分别追踪完成度
TESTING.mixed      = CODE 和 CONTENT 质量门禁并行，需双方通过方可进入 DELIVERY
```

PROJECT_MEMORY.md 增加可选字段：

```yaml
mixed_type_context:           # 混合型项目专用，非混合型为 null
  primary_type: "DEV"
  secondary_types: ["COURSE"]
  weave_matrix: "DEVXCOURSE"
  sub_progress:
    dev_step_c_complete: false
    course_step_c_complete: false
  joint_gates_passed: []
```

### D2.2 跨模型验证的状态记录

## D3. 安全设计

### D3.1 跨模型安全策略差异适配（推迟决策 #1 落地）

**问题**：不同模型对安全指令的敏感度和执行方式不同：
- Claude：主动拒绝危险操作，安全偏好在模型层
- GPT-4o：依赖系统提示词的安全指令，需更显式的禁止声明
- Gemini：安全过滤在 API 层和提示词层双重作用
- DeepSeek-V3：中文安全指令遵循良好，英文安全指令可能被忽略

**设计方案：安全策略分级 + 模型适配表**

在 `modules/security_gate.md` 中新增模型适配章节：

| 安全检查项 | Claude | GPT-4o | Gemini | DeepSeek-V3 |
|-----------|--------|--------|--------|-------------|
| §2.1 输入净化器 | 标准 | 强化（显式包裹） | 标准 | 强化（中文优先） |
| §2.2 记忆写入门禁 | 标准 | 强化（二次校验） | 标准 | 标准 |
| §2.3 禁止函数清单 | 标准 | 强化（扩展清单） | 标准 | 标准 |
| 危险关键词检测 | 标准 | 强化（英文+中文） | 标准 | 强化（中文优先） |

### D3.2 模块数字签名验证（推迟决策 #2 落地）

**目的**：确保 `modules/` 下文件未被意外修改或篡改。

**设计方案**：最小可行签名方案

```
# modules/MODULE_CHECKSUMS.sha256
# 由 OmniPM 维护工具生成，Agent 在加载模块前校验
6a0c2b9c...  modules/roles.md
f1e3d5a7...  modules/router_logic.md
8b4c1e9d...  modules/design-dimensions.md
...
```

Agent 在 §9.4 模块加载时新增校验步骤：
1. 计算目标模块 SHA256
2. 与 `MODULE_CHECKSUMS` 对比
3. 不一致 → 告警并拒绝加载："模块 [名称] 校验失败，可能已被修改。请确认文件完整性后重试。"

**文件变更**：
- 新建 `modules/MODULE_CHECKSUMS.sha256`
- 修改 `OMNIPM_SYSTEM_PROMPT.md` §9.4，新增校验步骤

## D4. 性能与可伸缩性（Token 效率）

### D4.1 Token 成本跟踪反馈机制（推迟决策 #5 落地）

**设计方案：轻量级 Token 记账**

在每个阶段出口（`[STEP_X_COMPLETE]` 块）追加 Token 消耗摘要：

```
[STEP_C_COMPLETE] · Token 消耗: ~12,500 (累计 ~38,200)
  输入: ~8,200 | 输出: ~4,300 | 缓存命中: ~2,100 (16%)
```

此数据由 Agent 估算（非精确计数），用于用户感知成本。不依赖 API 返回的精确 usage 数据（跨模型不可用）。

### D4.2 前缀缓存优化

**问题**：OmniPM 主提示词约 1,000 行（~15K tokens），每次会话需完整加载。不同模型的前缀缓存策略不同：
- Claude：自动前缀缓存，固定前缀命中率高
- GPT-4o：自动缓存，但非固定前缀（如时间戳、session_id）会破缓存
- Gemini：上下文缓存 API，需显式创建
- DeepSeek-V3：支持前缀缓存，策略类似 Claude

**优化方案**：

1. **固定前缀最大化**：将 15 章主提示词中不变的部分（状态机、协议、格式规范）放在最前面，动态内容（时间戳、session id、项目名）推后或用 `{{PLACEHOLDER}}` 替代
2. **缓存边界对齐**：每 4K token 边界处放置章节分隔符 `---`，帮助模型识别缓存断点
3. **禁止缓存破坏模式**：不在主提示词中插入绝对时间戳（`2026-07-21T14:30:00Z` → `{{CURRENT_DATETIME}}`），时间戳只在会话消息中传递

### D4.3 Token 预算控制

新增 `§3.6 Token 预算控制`（可选项，默认关闭）：

```
用户可通过"预算:X tokens"指令设置单阶段 Token 上限。
Agent 在接近预算时自动精简输出（合并冗余块、省略次要细节），
并在预算耗尽前提示用户是否追加。
```

## D5. 可观测性

### D5.1 长会话行为退化监控（推迟决策 #4 落地）

**问题**：LLM 在超长上下文（>50K tokens）中可能出现：
- 状态机转换遗漏（跳过 GATE 等待用户确认）
- 输出格式退化（忘记 `[STEP_X_COMPLETE]` 块）
- 安全检查衰减（跳过禁止函数扫描）

**设计方案：自检探针**

在 `§3.3 单阶段执行循环` 的每个 Step 出口增加自检探针：

```
[STEP_X_COMPLETE] 自检探针：
✅ 状态机路径合法：REQUIREMENT_ALIGNMENT → PLANNING → DESIGN
✅ GATE 确认完成：用户已回复"确认"
✅ 安全门禁执行：禁止函数扫描完成，0 命中
✅ 格式块完整：STATUS_BLOCK ✓ | DECISION_BLOCK ✓ | DOC_BLOCK ✓
⚠️ 会话深度：当前 ~42,000 tokens，退化风险：低
```

退化风险评级：
- **低**（<50K tokens）：正常执行
- **中**（50K-100K tokens）：增强心跳频率，每子步骤输出格式自检
- **高**（>100K tokens）：建议用户开新会话，使用 CHECKPOINT 恢复

### D5.2 跨模型行为偏差度量

定义 **行为偏差分数（BDS, Behavioral Deviation Score）**：

```
BDS = Σ(各测试用例的偏差分 × 用例权重) / 总权重

单用例偏差分计算：
- 状态机转换路径偏差：每跳转错误 +3
- GATE 确认行为偏差：跳过确认 +5，误判确认信号 +3
- 输出格式偏差：缺少必须块 +2/块
- 安全扫描偏差：跳过扫描 +5
- 专家评审格式偏差：格式错误 +1/专家

目标：BDS ≤ 10（满分 100，即 ≥90% 一致性）
```

### D6.1 测试套件设计（TEST_SUITE.md）

### D6.2 LLM-as-Judge 自动化验证（推迟决策 #3 落地）

**目的**：在 Step B 专家评审后，用一个独立的 LLM 调用审查评审质量。

**设计方案**：轻量级审查提示词

```markdown
## LLM-as-Judge 审查提示词
你是 OmniPM 评审质量审查员。审查以下专家评审记录，评估：

1. **完整性**：每位专家是否输出了至少 3 条具体建议？
2. **严重等级合理性**：P0/P1/P2 标注是否与其描述的风险程度匹配？
3. **交叉覆盖**：是否有两位专家对同一议题给出了矛盾建议？标注冲突点。
4. **遗漏检查**：是否有明显未覆盖的评审盲区？指出。

输出格式：
- 完整性得分：X/8
- 严重等级偏差：列出标注不当的建议
- 冲突检测：列出矛盾建议对
- 遗漏盲区：列出未覆盖的关注领域
```

**调用时机**：Step B 评审结束后，Agent 内部调用（非交互式），结果写入 PROJECT_DECISIONS.md。

### D6.3 跨模型验证流水线

```
验证流水线（人工触发：/validate-cross-model）
    │
    ├─ Step 1：加载 CROSS_MODEL_TEST_SUITE.md
    │
    ├─ Step 2：对每个目标模型执行 20 个测试用例
    │    │  记录：路由结果、状态转换路径、输出格式、安全行为
    │    │
    │    └─ 每个用例标记 passed/failed + deviation_score
    │
    ├─ Step 3：计算 BDS（行为偏差分数）
    │
    ├─ Step 4：生成《跨模型兼容性验证报告》
    │    │  含：总BDS、各模型BDS、各用例通过率、已知不兼容项
    │    │
    │    └─ 判定：BDS ≤ 10 → 兼容 ✅ | BDS 11-25 → 兼容⚠️ | BDS > 25 → 不兼容 ❌
    │
    └─ Step 5：更新 MODEL_PROFILES.md（补充新发现的模型行为特征）
```

## D7. 合规与质量标准

### D7.1 跨模型行为一致性标准

| 维度 | 目标 | 测量方法 |
|------|------|---------|
| 路由准确性 | ≥95% 一致 | 6 个路由用例，模型间路由结果一致比例 |
| 状态机转换 | ≥90% 一致 | 路径合法、无跳步、无死锁 |
| GATE 确认 | ≥95% 一致 | 正确的确认/拒绝信号识别 |
| 安全扫描 | 100% 一致 | 禁止函数/敏感信息/注入 不可跳过 |
| 输出格式 | ≥85% 一致 | 5 种 OUTPUT_BLOCK 完整性 |
| 专家评审 | ≥80% 一致 | 格式模板遵循、严重等级标注 |
