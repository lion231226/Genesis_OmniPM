# 瑜伽馆SaaS — 微信消息推送技术方案

> 生成日期: 2026-07-22 | 架构评审产出 | v1.0

---

## 当前方案：三通道混合架构（官方认可）

| 通道 | 适用对象 | 场景 | 限制 | 成本 |
|------|---------|------|------|------|
| 小程序订阅消息 | C端客户 | 约课提醒/签到确认/排队通知/积分阈值 | 一次性订阅，用户每次操作换1次推送权 | 免费 |
| 短信 | C端保底 | 课前提醒降级/流失预警 | 0.04元/条 | ~48元/月/门店 |
| 企业微信应用消息 | B端老板 | 日报/周报/月报/预警 | 需安装企业微信 | 免费 |
| 小程序消息中心 | C端拉取 | 课表/报告/成就/关怀 | 不推送，红点引导用户查看 | 免费 |

## 未来升级方向：非官方通道技术方案

> ⚠️ 以下方案均涉及微信个人号/企业微信的非官方使用方式，存在封号风险，
> 仅作为技术储备和特定场景的降级方案，不作为产品默认推荐。

### 方案一：纯视觉自动化（Pure Visual / CV Approach）

**核心思路**：通过计算机视觉 + UI自动化，模拟真人在微信客户端上的操作，
实现消息的读取和发送。

**技术栈**：
```
物理层: 安卓手机（真机或云手机）或 Windows 微信客户端
视觉层: OCR（PaddleOCR/Tesseract）+ 模板匹配（OpenCV）
控制层: ADB（安卓）/ Win32 API + 无障碍服务 / minitouch
编排层: Appium / uiautomator2 / 自研框架
AI层:   YOLO目标检测（定位微信UI元素）+ 意图识别（NLU）
```

**实现路径**：
```
1. 截屏 → OCR识别当前页面状态（聊天列表/对话框/通讯录）
2. YOLO检测关键UI元素（发送按钮/输入框/联系人头像）
3. 坐标映射 → 模拟点击/滑动/输入
4. 闭环验证：发送后再次截屏确认消息已出现在对话框中
```

**优势**：
- 微信无法检测（模拟真人操作，非协议/注入层）
- 不受微信版本更新影响（不依赖内部API/Web接口）
- 可发送任意内容（文本/图片/小程序卡片）
- 完全白盒可控

**劣势**：
- 延迟高（截屏+OCR+操作，单条消息 3-8 秒）
- 并发受限（一台设备同时只能操作一个微信）
- 设备成本（每个微信账号需要独立设备或云手机实例）
- OCR准确率非100%，复杂页面可能识别失败
- 微信客户端更新可能导致UI变化（需维护元素定位模板）

**适用场景**：
- 高价值客户的一对一关怀消息（量少但要求必达）
- 老板日报/紧急预警的保底通道
- 需要发送图片/小程序卡片等富媒体内容

**设备方案对比**：

| 方案 | 单机成本 | 稳定性 | 延迟 | 可扩展性 |
|------|---------|--------|------|---------|
| 真机+ADB | 300-800元/台 | 高 | 3-5秒 | 差（物理设备管理） |
| 云手机（红手指/多多云） | 30-50元/月/台 | 中 | 5-8秒 | 好（API批量管理） |
| Windows微信+Win32 | 0元（复用服务器） | 中 | 2-4秒 | 中（受Windows桌面限制） |
| ARM集群（树莓派+Android） | 200元/台 | 中高 | 4-6秒 | 好（可堆叠） |

**推荐原型方案**：Windows微信 + Win32 API + OCR
- 成本最低（零硬件投入）
- 延迟最低（2-4秒/条）
- 适合小规模试点（< 50条/天）

### 方案二：微信Web协议逆向（WeChat Web Protocol）

**核心思路**：逆向微信网页版/Windows版的通信协议，直接发送HTTP/WebSocket请求。

**技术栈**：
- 协议分析：Wireshark/Fiddler 抓包 + 反编译
- 实现：Python/Node.js 模拟微信协议请求
- 开源参考：wechaty（Puppet层）、itchat（已不可用）

**优势**：
- 延迟极低（< 500ms）
- 可高并发（纯HTTP请求，无UI层限制）
- 成本极低（无需设备）

**劣势**：
- 🔴 高风险封号（微信主动检测协议层异常）
- Web微信已基本停止服务（2022年起大规模封禁）
- Windows微信协议频繁更新，维护成本高
- 法律灰色地带（违反微信用户协议）

**结论**：❌ 不推荐。风险远大于收益。

### 方案三：企业微信机器人 + 个人微信互通

**核心思路**：利用企业微信的"客户联系"功能，将个人微信好友导入企业微信客户库，
通过企业微信官方API发送消息，用户在个人微信上接收。

**技术栈**：
- 企业微信官方API（`/cgi-bin/message/send`）
- 客户联系（Customer Contact）模块
- 企业微信后台管理

**优势**：
- ✅ 官方认可，零封号风险
- 支持群发、标签推送、欢迎语
- 支持小程序卡片、图片、文件

**劣势**：
- 需将客户添加为企业微信"外部联系人"（有好友上限）
- 部分消息类型受限（模板消息需审批）
- 需维护企业微信后台

**适用场景**：
- 已经使用企业微信管理客户的瑜伽馆
- 替代方案一作为"合规升级版"

---

### 方案四：RPA + 微信（低代码视觉）

**核心思路**：使用商业RPA工具（影刀/UiPath/来也）编写微信操作脚本。

**技术栈**：
- 影刀 RPA（国产，微信生态支持好）
- 模板化操作流程（登录→查找联系人→发送消息→确认发送）

**优势**：
- 低代码，瑜伽馆老板可自行维护
- 影刀等国产RPA对微信有专门适配
- 可视化调试

**劣势**：
- 同样受视觉方案的速度限制
- RPA工具授权费用
- 不适合高频/大批量场景

**适用场景**：
- 非技术团队的过渡方案
- 临时活动通知

## 推荐演进路线

```
Phase 1 (当前):  官方三通道 — 覆盖80%场景
                  小程序订阅消息 + 短信 + 企业微信 + 消息中心

Phase 2 (升级):  CV视觉保底 — 覆盖剩余20%高价值场景
                  Windows微信 + OCR，用于老板日报/关键客户关怀

Phase 3 (远期):  企业微信互通 — 合规替代CV方案
                  将C端客户导入企业微信客户库，全量走官方API
```
